C05 — Detailed Design

Od architektury k návrhovému záměru a unit testům

Proč Detailed Design?

V C03 jste rozhodli kde budou hlavní odpovědnosti a hranice systému. Detailed Design jde o úroveň níž a říká jak má být konkrétní software unit / component uvnitř navržena, aby:

• byl explicitní návrhový záměr;

• byly jasné významné metody, operace, algoritmy, data a stavy;

• byla jasná rozhraní a kontrakty;

• šlo z návrhu přímo odvodit unit/component testy;

• implementace nebyla jen „kód, který zrovna funguje“.

**DD je technický základ pro implementaci a unit verification. Není to zpětný popis hotového kódu.**

Co budete dělat

1. Vyberete jednu architecture responsibility / software unit.

2. Odvodíte její detailed responsibilities.

3. Navrhnete structure, data/state a interfaces.

4. Navrhnete methods, algorithms a dynamic behavior.

5. Odvodíte unit/component testy z DD.

6. Implementujete a ověříte design ↔ code consistency.

I jednoduchý systém má DD

Například objednání jízdenky:

BuyTicket
 ├─ validate request
 ├─ determine fare
 ├─ calculate price
 ├─ reserve seat
 ├─ create ticket
 └─ persist result

DD neznamená přidat deset tříd. Znamená například explicitně rozhodnout:

• kdo vybírá tarif;

• kde je algoritmus ceny;

• jaké jsou vstupy/výstupy;

• pre/postconditions;

• failure behavior;

• které unit testy z toho vyplývají.

2 — Odvoďte detailed responsibilities

Proč?

Nejdřív potřebujete vědět, co všechno musí jednotka uvnitř rozhodnout nebo udělat. Až potom dává smysl řešit classes a methods.

Co udělat?

Rozložte vybranou responsibility na 3–7 menších responsibilities.

Příklad — Ticket Pricing:

- identify passenger category
- select applicable fare
- calculate base price
- apply discount / surcharge
- validate pricing conditions
- return final price + reason

|---|---|
| ... | ... |

Smysl kroku

Vzniká functional / responsibility view na úrovni DD — návrhový záměr před konkrétní strukturou.

3 — Navrhněte structure, data/state a interfaces

Proč?

Teď rozhodujete kdo co vlastní, která data/state používá a přes jaký contract spolu prvky komunikují. To je základ implementace i test isolation.

Co udělat?

Přiřaďte responsibilities konkrétním design elements: class, module, component, policy, value object, repository, adapter, interface.

Výstup

| Responsibility | Owner | State/data | Why here? |
|---|---|---|---|
| ... | ... | ... | ... |

Interface / contract

Definujte alespoň jedno významné interface.

Příklad:

<<interface>> FarePolicy

calculate(passenger, connection, ticketType) : PriceResult

Contract:

Preconditions:
- passenger category known
- connection valid

Postcondition:
- PriceResult contains final price and applied fare

Failures:
- UNSUPPORTED_FARE
- INVALID_INPUT

Focused UML structural view

Nakreslete jeden focused UML class/component/package diagram. Přibližně 4–8 významných prvků. Ukažte interfaces, dependencies a důležité state/data ownership.

Smysl kroku

Z diagramu musí být zřejmé jak je design rozdělen a přes jaké contracts se jeho části propojují.

Proč?

Strukturální diagram nestačí. Unit verification často vychází právě z methods, pre/postconditions, algorithms, branches, state transitions a error behavior.

Significant methods / operations

U významných operací uveďte:

Nedokumentujte getters/setters, triviální delegaci ani framework boilerplate.

Algorithm / decision logic

Pokud existuje významný algoritmus nebo business rule, udělejte jej explicitní pomocí pseudocode, activity diagramu, decision table nebo state machine.

Příklad:

base = fareTable[connection]
if passenger.student:
    base = base * studentFactor
if ticket.firstClass:
    base = base + firstClassSurcharge
return Money.round(base)

Detailed sequence

Ukažte jeden významný scénář uvnitř jednotky.

C03 architecture level:

API → Reservation Management → Availability → Persistence

C05 DD level:

ReservationService → PolicyResolver → AvailabilityPolicy → ReservationRepository

Smysl kroku

Musí být explicitní jak návrh skutečně realizuje významné chování uvnitř jednotky.

5 — Odvoďte unit/component testy z DD

Proč?

Tohle je jeden z hlavních důvodů DD. Jakmile máte contracts, methods, algorithms, state transitions a failure behavior, můžete z nich přímo odvodit verification.

**Unit tests ověřují návrhový záměr jednotky, ne jen současnou implementaci.**

Výstup

Minimálně 5 testů:

| DD element / decision | What must hold? | Test level | Test case |
|---|---|---|---|
| interface contract | ... | unit/component | ... |
| algorithm branch | ... | unit | ... |
| state transition | ... | unit/component | ... |
| failure behavior | ... | unit | ... |
| collaboration | ... | component/integration | ... |

U alespoň dvou testů vysvětlete:

Selected level:
Why this level:
What design decision does this test verify?

Smysl kroku

Musí být vidět přímá vazba DD decision → verification.

6 — Implementujte a ověřte design ↔ code

Proč?

DD je návrhový záměr. Implementace jej musí realizovat — nebo musí být vědomě změněn samotný design.

Co udělat?

Implementujte navržený slice a porovnejte planned DD vs actual implementation.

Výstup

| DD decision | Implemented? | Evidence | Action |
|---|---|---|---|
| ... | YES/PARTLY/NO | file/test | keep / update DD / update code |

Smysl kroku

Pokud se design a code liší, neopravujte automaticky diagram podle kódu. Rozhodněte, co je správně.

Jak hluboko má DD jít?

DD má být tak hluboký, aby bylo možné:

1. implementovat významná rozhodnutí bez hádání;

2. odvodit unit/component tests;

3. pochopit algorithm / method / state behavior;

4. vidět významná interfaces a dependencies;

5. zachovat design intent při změně;

6. posoudit maintainability / extensibility tam, kde je relevantní.

Typicky mohou být explicitní:

responsibilities
classes / modules / components
interfaces and contracts
methods / operations
data structures
state and transitions
algorithms
decision logic
error handling
dependency direction
concurrency behavior
persistence behavior
configuration / variation points

Co může zůstat jen v kódu?

Typicky:

• jednoduché lokální statements;

• triviální private helper;

• getter/setter;

• framework boilerplate;

• syntax-level detail;

• detail bez významu pro verification nebo budoucí změnu.

Jak poznat, že je DD dostatečný?

1. **Implementation:** jiný developer chápe významná design decisions bez hádání.

2. **Unit verification:** z DD lze odvodit smysluplné unit/component tests.

3. **Change:** je jasné, kde se má změnit konkrétní rule nebo varianta.

C05 — Detailed Design

From Architecture to Design Intent and Unit Tests

Why Detailed Design?

In C03 you decided where major responsibilities and boundaries live. Detailed Design goes one level deeper and explains how a concrete software unit/component is intended to work internally, so that:

• design intent is explicit;

• significant methods, operations, algorithms, data and state are visible;

• interfaces and contracts are clear;

• unit/component tests can be derived directly from the design;

• implementation is not just “code that happens to work”.

**DD is a technical basis for implementation and unit verification. It is not a retrospective description of finished code.**

What will you do?

1. Select one architecture responsibility / software unit.

2. Derive detailed responsibilities.

3. Design structure, data/state and interfaces.

4. Design methods, algorithms and dynamic behavior.

5. Derive unit/component tests from DD.

6. Implement and verify design ↔ code consistency.

Even a simple system has DD

For a simple train-ticket system, do not invent complexity. But even `BuyTicket` may require explicit decisions about fare selection, pricing algorithm, inputs/outputs, pre/postconditions, failure behavior and unit tests.

1 — Select one architecture responsibility / software unit

Why?

DD refines one existing architectural responsibility internally. You are not redesigning the whole system.

What to do?

Select one C03 unit with real logic, e.g. Reservation lifecycle, Availability, Approval handling, Ticket pricing.

Related scenario(s):

Meaning

Why?

First determine what the unit must decide or perform internally. Only then decide classes and methods.

- select applicable fare
- calculate base price
- apply discount / surcharge
- validate pricing conditions
- return final price + reason

| Detailed responsibility | Why is it needed? |
|---|---|
| ... | ... |

Meaning

This is the functional / responsibility view at DD level — design intent before concrete structure.

3 — Design structure, data/state and interfaces

Why?

Now decide who owns each responsibility, which data/state it uses, and through which contract elements collaborate. This supports implementation and test isolation.

|---|---|---|---|
| ... | ... | ... | ... |

Define at least one meaningful interface.

<<interface>> FarePolicy

Contract:

Preconditions:
- passenger category known
- connection valid

Postcondition:
- PriceResult contains final price and applied fare

- UNSUPPORTED_FARE
- INVALID_INPUT

Meaning

The design structure and its contracts must be visible.

Why?

A structural diagram is not enough. Unit verification often follows from methods, pre/postconditions, algorithms, branches, state transitions and error behavior.

Meaning

Make explicit how significant behavior is realized inside the unit.

5 — Derive unit/component tests from DD

Why?

This is one of the main reasons for DD. Contracts, methods, algorithms, state transitions and failure behavior directly define verification needs.

**Unit tests verify design intent, not only the current implementation.**

Output

Create at least 5 tests:

| DD element / decision | What must hold? | Test level | Test case |
|---|---|---|---|
| interface contract | ... | unit/component | ... |
| algorithm branch | ... | unit | ... |
| state transition | ... | unit/component | ... |
| failure behavior | ... | unit | ... |
| collaboration | ... | component/integration | ... |

For at least two tests:

Selected level:
Why this level:
What design decision does this test verify?

Meaning

The link DD decision → verification must be explicit.

6 — Implement and verify design ↔ code

Why?

DD is design intent. Implementation must realize it, or the design must be consciously changed.

Output

| DD decision | Implemented? | Evidence | Action |
|---|---|---|---|
| ... | YES/PARTLY/NO | file/test | keep / update DD / update code |

Meaning

If design and code differ, do not automatically update the diagram to match the code. Decide what is correct.

How deep should DD go?

DD should be detailed enough to:

1. implement significant decisions without guessing;

2. derive unit/component tests;

3. understand algorithm / method / state behavior;

4. see significant interfaces and dependencies;

5. preserve design intent during change;

6. assess maintainability / extensibility where relevant.

Typical explicit content:

responsibilities
classes / modules / components
interfaces and contracts
methods / operations
data structures
state and transitions
algorithms
decision logic
error handling
dependency direction
concurrency behavior
persistence behavior
configuration / variation points

What can stay only in code?

Typically:

• simple local statements;

• trivial private helper;

• getter/setter;

• framework boilerplate;

• syntax-level detail;

• details irrelevant to verification or future change.

How do you know DD is sufficient?

1. **Implementation:** another developer understands significant decisions without guessing.

2. **Unit verification:** meaningful unit/component tests can be derived from DD.

3. **Change:** it is clear where a concrete rule or variant should change.

What do you submit?

Update `docs/architecture-and-decisions.md` with the DD and `docs/evidence-and-evolution.md` with tests, results, mismatches, remaining risk and commit/tag.
