SWI · C10 | Operations & logs

C10 — Co se v systému stalo a jak to poznáme?

Na svém Reservation Systemu vyzkoušejte několik provozních situací. Pracujte lokálně s testovacími daty. Zajímají nás skutečné výsledky, stav rezervací a užitečnost logů.

Co máte udělat

  1. Úspěšná operace. Vytvořte a potvrďte platnou rezervaci. Doložte, že vše proběhlo správně (například odpovědí aplikace a kontrolou uloženého stavu). Log úspěšné operace není povinný.
  2. Odmítnutí kolize. Zkuste potvrdit překrývající se rezervaci. Ověřte správné zamítnutí a stav dat. Rozhodněte, zda a proč má mít běžné doménové zamítnutí záznam v logu — nebo zda postačí odpověď aplikace. Nejde automaticky o technickou chybu.
  3. Technická porucha. Na izolované testovací instanci dočasně znepřístupněte databázi, proveďte operaci a poté databázi obnovte. Z logů zjistěte, kdy a kde problém nastal a jak aplikace reagovala. Pokud vaši DB nelze samostatně a bezpečně odpojit, použijte neplatnou testovací konfiguraci nebo výpadek existující závislosti.
  4. Restart a obnova provozu. Zastavte a znovu spusťte aplikaci. Ověřte, zda zůstala zachována potvrzená rezervace a zda lze provést další operaci. Podívejte se, co je o zastavení a startu vidět v dostupných záznamech.

U každé situace si předem určete očekávaný výsledek, po provedení zaznamenejte skutečnou reakci a ověřte stav, který je pro danou situaci důležitý. Poruchy vyvolávejte pouze na testovacích datech; pokud je výsledek transakce neznámý, neopakujte zápis naslepo.

Co posoudit u logování

Nelogujte všechno automaticky. U běžného úspěchu může stačit ověření výsledku; u zamítnutí zvažte účel záznamu (např. audit versus zbytečný šum). U technické poruchy by naopak měly být k dispozici informace použitelné pro diagnostiku: čas, komponenta nebo operace, typ problému a pozorovaný výsledek. Pokud důležitá informace chybí, doplňte minimální vhodný logovací záznam a pokus zopakujte. Bez hesel, tokenů a osobních údajů.

Pozor: log může říct, jak aplikace reagovala, ale není sám o sobě důkazem správného stavu databáze. Ten podle potřeby ověřte zvlášť.

C10 — What happened in the system, and how can we tell?

Try several operational situations using your Reservation System. Work locally with disposable test data. Focus on actual results, reservation state and the usefulness of logs.

What to do

  1. Successful operation. Create and confirm a valid reservation. Provide evidence that it worked correctly (for example, the application response and a persisted-state check). Logging every successful operation is not required.
  2. Conflict rejection. Attempt to confirm an overlapping reservation. Verify correct rejection and the resulting data state. Decide whether this ordinary business rejection needs a log record, and explain why — or whether the application response is sufficient. A rejected business operation is not automatically a technical error.
  3. Technical failure. Temporarily make the database unavailable in an isolated test instance, attempt an operation and then restore the database. Use logs to determine when and where the failure occurred and how the application reacted. If your database cannot be disconnected separately and safely, use invalid test configuration or failure of an existing dependency instead.
  4. Restart and recovery. Stop and restart the application. Verify that a previously confirmed reservation remains present and that a further operation works. Inspect which stop/start events are visible in the available records.

Before each situation, state the expected result. Afterwards, record the actual response and check the relevant state. Inject faults only with test data; never blindly retry a write when the transaction outcome is unknown.

What to decide about logging

Do not log everything by default. For a successful operation, checking the result may be enough. For a business rejection, consider whether an audit requirement justifies logging it or whether it would merely add noise. A technical failure, however, should leave useful diagnostic information: time, component or operation, failure type and observed outcome. If an essential detail is missing, add one minimal appropriate event and repeat the trial. Never log passwords, tokens or personal data.

Important: a log may show the application's reaction, but it cannot by itself prove the database state. Check authoritative state separately when needed.
