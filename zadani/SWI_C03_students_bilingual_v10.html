SWI C03 — Architecture

Od AS-IS implementace k přijaté architektuře

Cíl

Navrhnout a zdůvodnit architekturu pro vybranou část systému, propojit ji s požadavky a scénáři z C02 a ověřit, že ji implementace skutečně dodržuje.

V tomto průchodu se naučíte

  • odvodit architektonicky významné problémy a drivery z požadavků a evidence;
  • rozlišit doménové pojmy, odpovědnosti a jejich implementační umístění;
  • určit, které odpovědnosti a stav musí mít jasného vlastníka;
  • formulovat konkrétní architektonickou rozhodovací otázku;
  • vytvořit a porovnat více reálných architektonických alternativ;
  • ověřit alternativy na stejném scénáři, včetně failure / concurrency situace;
  • zaznamenat rozhodnutí a jeho důsledky pomocí ADR;
  • vytvořit konzistentní strukturální, dynamické a runtime pohledy na architekturu;
  • realizovat scénář pomocí sekvenčního a návrhového třídního diagramu;
  • kontrolovat konzistenci mezi požadavky, diagramy, rozhodnutími a kódem;
  • porovnat AS-IS implementaci s přijatou TO-BE architekturou;
  • řízeně upravit implementaci pouze tam, kde je to potřeba;
  • ověřit nejen funkční chování, ale i dodržení konkrétního architektonického pravidla.

Použijte:

  • Specification Baseline v0.2;
  • scénáře, pravidla/invarianty a statechart z C02;
  • ověřovací příklady z C02;
  • běžící aplikaci;
  • drivery přenesené z C02;
  • Část A — zmapování současné implementace.

Pokud jste Část A udělali v úterý, použijte ji jako hotový AS-IS podklad. Aktualizujte pouze položky, které jste od té doby skutečně změnili v kódu.

SWI C03 — Architecture

From AS-IS Implementation to an Accepted Architecture

Goal

Design and justify the architecture for a selected part of the system, connect it to the requirements and scenarios from C02, and verify that the implementation actually conforms to the accepted architecture.

What you will learn

  • derive architecture-significant problems and drivers from requirements and evidence;
  • distinguish domain concepts, responsibilities, and their implementation allocation;
  • identify which responsibilities and state require a clear owner;
  • formulate a concrete architecture decision question;
  • create and compare multiple realistic architecture alternatives;
  • evaluate alternatives using the same scenario, including a failure / concurrency situation;
  • record a decision and its consequences in an ADR;
  • create consistent structural, dynamic, and runtime views of the architecture;
  • realize a scenario with a design sequence diagram and focused design class diagram;
  • check consistency across requirements, diagrams, decisions, and code;
  • compare the AS-IS implementation with the accepted TO-BE architecture;
  • change the implementation only where the accepted design requires it;
  • verify not only functional behaviour but also conformance to a concrete architecture rule.

Use:

  • Specification Baseline v0.2;
  • scenarios, rules/invariants, and statechart from C02;
  • verification examples from C02;
  • the running application;
  • architecture drivers carried from C02;
  • Part A — mapping the current implementation.

If you completed Part A on Tuesday, use it as the finished AS-IS input. Update only items affected by code that your team actually changed afterwards.
