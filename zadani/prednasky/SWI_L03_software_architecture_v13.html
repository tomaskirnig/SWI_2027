SWI · L03 · Architecture 1/32

L03 — Software Architecture

Architecture is the discipline of making consequential structural decisions so important system claims remain true under execution, failure and change.

Reasoning

A useful architecture is not “a diagram of components”. It is a justified allocation of responsibility, state, boundaries, interactions and runtime constraints. The diagram is only the visible form of the decision.

Use in practice

Read every architectural model as an argument: this structure exists because this claim, risk, quality concern or expected change must be handled.

Concrete example

Claim: two conflicting reservations must not both become CONFIRMED. This claim will force decisions about lifecycle ownership, conflict evaluation and consistency boundary.

CLAIM → RESPONSIBILITY → BOUNDARY → DECISION → EVIDENCE
Detailed notes

The lecture remains case-led. Concepts appear when the Reservation case needs them. The aim is not to memorize architecture vocabulary, but to learn the reasoning behind structure.

SWI · L03 · Architecture 2/32

Architecture in this course

The course does not teach lifecycle labels as the main content. It teaches the engineering depth inside activities that every serious lifecycle must perform.

Reasoning

Scrum, Kanban, staged development, ASPICE-like process models or continuous delivery organize work differently. They do not remove the need to specify behavior, allocate responsibilities, evaluate quality, design implementation, verify and control change.

Use in practice

For each topic ask: what decision must be made, what artifact/code/evidence supports it, and what consequence follows?

Concrete example

L03 asks: we know what the system must do; how must the software be structured so that the claims survive realistic execution?

SPECIFICATION → ARCHITECTURE → QUALITY → DETAILED DESIGN → VERIFICATION → CHANGE
Detailed notes

This keeps architecture connected to the overall subject. The purpose is not to discuss “Waterfall vs Agile”, but to show what an engineer must be able to do in either setting.

SWI · L03 · Architecture 3/32

Start from claims, not boxes

A structural model is meaningful only when it protects or explains a concrete system claim.

Reasoning

Without claims, a component diagram can look professional but cannot be evaluated. With claims, every boundary and dependency can be challenged: does it help preserve the claim under change, failure or runtime stress?

Use in practice

Collect functional rules, invariants, constraints, quality concerns, external dependencies and expected changes. Convert them into architecture questions.

Concrete example

Invariant: no two CONFIRMED reservations may overlap the same exclusive Resource. Architecture question: where is the authoritative decision that enforces this?

Requirement / invariant / constraint
        ↓
Architecture question
        ↓
Structure with reason
Detailed notes

The word “claim” is deliberately broad. It includes requirements, business rules, safety/security assumptions, quality scenarios and constraints.

SWI · L03 · Architecture 4/32

Running case: Reservation System

A small reservation system is enough to expose real architecture forces: state, concurrency, external integration, delayed workflow, quality and change.

Reasoning

The domain is intentionally simple so attention stays on architecture reasoning. The same reasoning transfers to appointments, machines, labs, charging slots, vehicle service, hospital rooms or manufacturing resources.

Use in practice

Use the same case repeatedly. Do not restart reasoning from a new example for every concept; evolve the architecture as new pressure appears.

Concrete example

Core operations: Create, Check Availability, Confirm, Cancel. Later change: some resources require delayed Approval.

Reservation · Resource · TimeInterval · User · Approval
Detailed notes

The case is not an exercise dependency; it is a worked example for architectural thinking.

SWI · L03 · Architecture 5/32

A working implementation is not yet architecture

Controller → Service → Repository may run successfully and still leave ownership, consistency and failure semantics undefined.

Reasoning

Happy-path functionality proves that one scenario works in one controlled run. It does not prove that the system has stable boundaries or that its rules remain true under concurrency, failure or future change.

Use in practice

Treat the first implementation as AS-IS evidence. Ask what it actually guarantees and which decisions are merely implicit.

Concrete example

One request: load Reservation → check no conflict → set CONFIRMED → save. It works in a demo, but the invariant has not yet been stress-tested.

Controller → Service → Repository
(happy path passes)
Detailed notes

This is not criticism of simple architecture. Simple is good when it is justified. The problem is unexamined simplicity.

SWI · L03 · Architecture 6/32

Concurrency reveals the first architectural problem

A correct sequential scenario can violate a business invariant when two executions interleave.

Reasoning

If the check and the update are not protected by a suitable consistency boundary, two requests may both observe “no conflict” and then both commit. The code can look locally correct and still produce invalid system state.

Use in practice

Attack important scenarios with runtime conditions: concurrency, partial failure, delayed response, restart and changed external state.

Concrete example

A checks: no conflict. B checks: no conflict. A saves CONFIRMED. B saves CONFIRMED. The no-overlap invariant is broken.

A: check → none        B: check → none
A: save CONFIRMED    B: save CONFIRMED
✕ invariant violated
Detailed notes

This slide turns architecture from drawing into correctness reasoning. It explains why architecture must include runtime behavior.

SWI · L03 · Architecture 7/32

Driver means pressure, not mechanism

The architecture driver is the reason the architecture must respond; transaction, event bus or microservice are possible responses, not the reason itself.

Reasoning

Premature solution names hide the real engineering question. A driver should make clear what could go wrong or what must be supported if the architecture ignores it.

Use in practice

Write drivers as: evidence → why it matters → architecture question. Leave mechanisms undecided until alternatives are compared.

Concrete example

Evidence: concurrent confirmations can race. Question: where is the authoritative confirmation decision? Mechanisms still open: transaction, DB constraint, optimistic locking, serialization.

Evidence → impact → architecture question → candidate mechanisms later
Detailed notes

In automotive/security/safety language this resembles separating a risk/control need from the technical implementation of the control.

SWI · L03 · Architecture 8/32

Responsibilities before components

Before naming components, identify the decisions, state and rules that somebody must own.

Reasoning

Mapping one use case to one service often duplicates business decisions. Architecture should first discover responsibilities that cut across scenarios and must remain consistent.

Use in practice

For one important scenario, list what must be decided, what state must be changed, what rule must hold and what result must be persisted or communicated.

Concrete example

Confirm Reservation: accept command, load state, validate lifecycle, evaluate conflicts, preserve invariant, change state, persist result, report outcome.

Scenario + rules
   ↓
Responsibilities
   ↓
Allocation to elements
Detailed notes

Responsibility analysis is the bridge between requirements and structure. It is not yet a component diagram.

SWI · L03 · Architecture 9/32

Boundaries must localize a reason

A boundary is useful when it localizes responsibility, state, policy, failure, trust, ownership or expected change.

Reasoning

Adding boundaries increases indirection and can increase operational complexity. Removing boundaries can spread decisions and make change unsafe. The value comes from the reason localized by the boundary.

Use in practice

For every boundary, be able to say: this boundary exists to localize ___ . If the blank cannot be filled, the boundary may be decorative.

Concrete example

Notification Integration exists to isolate external API failure and vendor SDK change from Reservation business logic.

Boundary localizes:
responsibility · state · policy · failure · trust · change
Detailed notes

This is applicable far beyond reservation systems: automotive ECUs, cloud services, enterprise apps and embedded systems all need meaningful boundaries.

SWI · L03 · Architecture 10/32

Structural level L0: Context

The context view answers what is inside the system and what is outside its control boundary.

Reasoning

Many architecture errors begin when an external system is treated as if it were internal, or when the application delegates a decision that it should own.

Use in practice

Draw the system as one box. Add only external actors/systems. Label what crosses the boundary. Do not add internal components here.

Concrete example

User/Approver sends commands. IdP provides identity claims. Notification Service receives notification requests. The application still owns authorization policy.

User / Approver → [Reservation System] → IdP
[Reservation System] → Notification Service
Detailed notes

Context is L0 because it deliberately hides internal structure. Its purpose is boundary and external dependency clarity.

SWI · L03 · Architecture 11/32

Structural level L1: Logical architecture

The logical architecture view answers where major responsibilities, state ownership and allowed dependencies live.

Reasoning

This is the first structural model that says how the system is organized. It is still independent of deployment: a logical element may be a module today and a service later.

Use in practice

Use 3–8 logical elements. For each element show name, responsibility, owned state/rule if any, and important dependencies.

Concrete example

Reservation Management owns lifecycle. Availability evaluates conflicts. Approval Workflow owns approval state. Notification Integration owns external notification boundary.

Reservation Management → Availability
Reservation Management → Persistence
Reservation Management → Notification Integration
Detailed notes

This is the central static architecture model. It should not be a folder tree and should not already imply deployment unless runtime is the question.

SWI · L03 · Architecture 12/32

Structural level L2: Modules, interfaces, adapters

L2 refines L1 boundaries into interfaces and adapters where a dependency or external boundary needs explicit control.

Reasoning

Not every dependency deserves an interface. Interfaces are introduced when variation, testing, failure isolation, ownership or technology boundary makes the dependency significant.

Use in practice

Use L2 when you need to show ports/adapters, repository interfaces, external SDK isolation, anti-corruption layers or dependency direction rules.

Concrete example

NotificationPort is used by Reservation Management. NotificationAdapter implements it and is the only element that knows the vendor Notification API.

Reservation Management → NotificationPort
NotificationAdapter → Vendor Notification API
Detailed notes

This level connects architecture to implementable constraints without descending into all classes.

SWI · L03 · Architecture 13/32

Structural level L3: Focused design classes

A class view belongs in architecture only when it clarifies ownership or collaboration that has architectural consequence.

Reasoning

A complete dump of classes is rarely useful. A focused class view is useful when it shows which class/interface owns a rule, policy, transition or collaboration needed by the architecture.

Use in practice

Use 4–10 classes/interfaces tied to one scenario. Show only operations and relationships needed to explain responsibility and interaction.

Concrete example

Reservation, TimeInterval, AvailabilityPolicy, ReservationRepository, ReservationApplication. The view explains who owns confirm() and conflict evaluation.

ReservationApplication → Reservation
ReservationApplication → AvailabilityPolicy
ReservationRepository <<interface>>
Detailed notes

This is the handoff edge to Detailed Design. Detailed design later expands local class structure, cohesion/coupling and patterns.

SWI · L03 · Architecture 14/32

Domain view: problem structure, not software structure

The domain view captures business concepts and rules that the architecture must respect, but it is not automatically the software design.

Reasoning

Using the same nouns in domain and code can mislead. A domain concept may become an entity, value object, policy, database constraint or just part of an interface contract.

Use in practice

Model concepts, relationships, multiplicities and important rules. Keep controllers, repositories, HTTP clients and frameworks out.

Concrete example

Reservation has TimeInterval and Resource. Resource can be exclusive or capacity-based. Approval may be associated with Reservation.

User 1 — * Reservation
Reservation 1 — 1 TimeInterval
Resource 1 — * Reservation
Reservation 0..1 — 1 Approval
Detailed notes

The domain view is often needed before structural allocation so that software boundaries do not erase business meaning.

SWI · L03 · Architecture 15/32

State view: lifecycle + transition ownership

A statechart shows legal states; architecture must add who owns the decision to move between them.

Reasoning

A lifecycle diagram alone does not protect behavior. If controllers, services and adapters can all change state, the diagram is documentation but not authority.

Use in practice

Use a statechart plus ownership table: transition → decision owner → who may request it → where it is persisted.

Concrete example

PENDING_APPROVAL → CONFIRMED may be requested by Approver, decided by Approval Workflow or Reservation Management, and stored in Reservation state.

DRAFT → PENDING_APPROVAL → CONFIRMED
             ↘ REJECTED / EXPIRED / CANCELLED
Transition owner table required
Detailed notes

This is a common gap in student and professional architecture documents: states are named, but ownership of transitions is not defined.

SWI · L03 · Architecture 16/32

Source of truth and consistency boundary

Architecture must define which data is authoritative, which state may be derived and which updates must be consistent together.

Reasoning

A database stores values, but it does not automatically own business decisions. Shared storage often hides unclear ownership and inconsistent updates.

Use in practice

Mark source of truth, transition owner, consistency boundary and any eventually consistent/read-model data.

Concrete example

Reservation DB stores state. Reservation Management owns lifecycle transition. Notification delivery status may be eventually consistent and retried independently.

stored value ≠ decision owner
source of truth · consistency boundary · derived state
Detailed notes

This reasoning maps directly to distributed systems, automotive zoning, data ownership across services and safety/security boundaries.

SWI · L03 · Architecture 17/32

Dynamic level D0: System sequence

A system sequence shows the interaction between actor and system without exposing internal structure.

Reasoning

It is useful when the architectural question is still about externally visible operations, not internal allocation.

Use in practice

Use it to clarify system operations and externally observable outcomes before diving into architecture participants.

Concrete example

User → Reservation System: confirmReservation(id). System → User: confirmed or conflict rejected.

Actor → System.confirmReservation(id)
System → Actor: outcome
Detailed notes

This level is close to requirements. It should not pretend to explain internal architecture.

SWI · L03 · Architecture 18/32

Dynamic level D1: Architecture sequence

An architecture sequence shows how logical architectural elements collaborate to realize a significant scenario.

Reasoning

This is where static architecture is tested dynamically. The sequence should reveal decision ownership, state change, boundary crossings and failure points.

Use in practice

Use participants from the L1/L2 static architecture. Show business decisions and architecturally relevant calls, not every method call.

Concrete example

User → API → Reservation Management → Availability → Persistence. alt conflict: reject without state change.

User → API → Reservation Management → Availability → Persistence
alt conflict → reject
Detailed notes

This is the main dynamic architecture view for L03.

SWI · L03 · Architecture 19/32

Dynamic level D2: Detailed object sequence

A detailed object sequence belongs mostly to design, but it can support architecture when it explains ownership inside one boundary.

Reasoning

Too much detail hides architectural meaning. Too little detail hides whether an important responsibility can actually be realized.

Use in practice

Use it only for a focused slice: the classes/interfaces that realize one architectural responsibility or rule.

Concrete example

ReservationApplication.confirm() calls Reservation.canConfirm(), AvailabilityPolicy.hasConflict(), then Reservation.confirm().

ReservationApplication → Reservation
ReservationApplication → AvailabilityPolicy
Reservation.confirm()
Detailed notes

This view should not be a full call trace. It is a focused realization of an architectural responsibility.

SWI · L03 · Architecture 20/32

Failure and concurrency timelines

Some dynamic questions are better answered by a timeline than by a classic sequence diagram.

Reasoning

Failure semantics depend on time order, commit points, retry, idempotency and what the caller has already observed.

Use in practice

Use a timeline when the key question is what has already happened when something fails or repeats.

Concrete example

CONFIRMED saved → Notification call times out → user already saw success → retry sends notification later.

commit CONFIRMED → notify() timeout → retry later
Questions: rollback? duplicate? observe?
Detailed notes

This widens “dynamic view” beyond UML sequences while keeping the same purpose: reason about execution.

SWI · L03 · Architecture 21/32

Runtime/deployment view

Runtime view answers where logical elements actually execute and what runtime failure/operation boundaries exist.

Reasoning

Logical separation is not deployment separation. Turning a module into a service adds network failure, deployment complexity, observability needs and operational ownership.

Use in practice

Map logical elements to processes/deployables, databases, external systems and nodes/zones where relevant.

Concrete example

One Reservation Application process contains Reservation Management, Approval Workflow and Notification Integration. PostgreSQL, IdP and Notification Service are separate runtime elements.

Logical modules → one application process
Application → PostgreSQL / IdP / Notification Service
Detailed notes

This is especially important in modern and automotive contexts where runtime topology has strong consequences.

SWI · L03 · Architecture 22/32

Which view when? Practical selection rule

Draw the smallest view that answers the current architecture question.

Reasoning

A fixed diagram checklist creates work without insight. View selection should follow concern and decision need.

Use in practice

Ask the question first, then choose the view level. If the view does not support a decision, reduce or remove it.

Concrete example

Inside/outside? Context. Who owns state? State ownership. Who collaborates? Architecture sequence. Where does it run? Runtime mapping. What class owns the rule? Focused class view.

question → view → decision/evidence
not: notation → diagram → hope
Detailed notes

This slide directly addresses when to create structural, dynamic, state and runtime models.

SWI · L03 · Architecture 23/32

Architecture baseline: expected end result

The result of architecture work is a connected baseline of decisions, models and evidence — not one final diagram.

Reasoning

A single component diagram cannot express drivers, alternatives, state ownership, runtime mapping, failure semantics and implementation constraints.

Use in practice

At the end, the baseline should explain what was decided, why, how it is represented, how code must follow it and what risk remains.

Concrete example

Drivers; decision question; alternatives; ADR; context; domain; logical static view; sequence; state ownership; runtime mapping; AS-IS/TO-BE delta; conformance rule; open risks.

drivers → ADR → views → implementation constraints → evidence → open risks
Detailed notes

This is the concrete answer to “what models should exist at the end of architecture?”

SWI · L03 · Architecture 24/32

Alternatives answer one decision question

Architecture alternatives are meaningful only when they are different answers to the same question.

Reasoning

Comparing arbitrary styles is weak. “Layered vs microservices vs event-driven” may compare categories that can coexist. A decision question creates a fair comparison.

Use in practice

State the question first. Sketch two materially different alternatives. Compare them against the same drivers and scenario.

Concrete example

Question: where should delayed approval workflow live? A: same deployable module. B: independent worker/service.

Decision question
 A: same deployable
 B: independent worker/service
Detailed notes

Architecture style vocabulary is useful only after the problem is framed.

SWI · L03 · Architecture 25/32

Walk alternatives through the same scenario

Scenario walkthrough reveals consequences that a pros/cons table can hide.

Reasoning

The important difference between alternatives is often visible only when state, failure, retry or delayed response occurs.

Use in practice

Use a table: step/event → Alternative A behavior → Alternative B behavior → risk/trade-off.

Concrete example

Approval arrives after request ends; Resource changed meanwhile; revalidate before final confirm; compare where state lives and who retries.

scenario step | A | B | consequence
Detailed notes

This is a lightweight version of scenario-based architecture evaluation.

SWI · L03 · Architecture 26/32

ADR records the reasoning memory

ADR preserves why a consequential architecture decision was made, including the downside accepted at the time.

Reasoning

Future maintainers see what exists in code. They often cannot see what was rejected, which driver mattered or when the decision should be revisited.

Use in practice

Record context, drivers, alternatives, decision, reason, accepted negative consequences and reconsideration trigger.

Concrete example

Keep Approval inside the same deployable until independent scaling or ownership becomes a real driver.

context → alternatives → decision → accepted downside → reconsider when
Detailed notes

An ADR without negative consequence is usually just a preference statement.

SWI · L03 · Architecture 27/32

Cross-view consistency is the quality gate

Architecture becomes credible when different views describe the same decisions without contradiction.

Reasoning

Each view can look correct alone. The actual architecture is the consistent set of decisions across views and code.

Use in practice

Check static ↔ sequence ↔ state ↔ runtime ↔ implementation. Fix mismatches before changing code further.

Concrete example

Static view says only Reservation Management changes lifecycle state, but code shows Controller writing state directly. This is architecture drift.

static ↔ sequence ↔ state ↔ runtime ↔ code
Detailed notes

This is a major expert skill: finding inconsistencies between views.

SWI · L03 · Architecture 28/32

AS-IS → TO-BE delta drives code change

Architecture should drive only necessary implementation changes, not decorative refactoring.

Reasoning

If the current implementation already conforms to the accepted decision, keep it. If it violates the decision, change it. If unclear, verify it.

Use in practice

Use a delta table with actions CHANGE, KEEP, VERIFY.

Concrete example

AS-IS: Notification SDK in application logic. TO-BE: isolated Notification Integration. Action: CHANGE.

AS-IS | TO-BE | action
CHANGE · KEEP · VERIFY
Detailed notes

This connects architecture to code economically and prevents architecture exercises from becoming random rewrites.

SWI · L03 · Architecture 29/32

Conformance protects architecture during change

A conformance check is valuable only when it protects a concrete architecture rule derived from a decision.

Reasoning

“We have architecture tests” is not enough. The check must prevent a meaningful decision from silently eroding.

Use in practice

Turn the decision into an explicit rule and make a repeatable check: static analysis, dependency test, repository query, review rule or runtime evidence.

Concrete example

Decision: lifecycle owner controls Reservation state. Rule: Controller/Adapter must not write Reservation.state directly.

decision → rule → repeatable check → evidence
Detailed notes

This becomes increasingly important when code is generated or changed quickly.

SWI · L03 · Architecture 30/32

Quality attributes reshape architecture

Quality concerns are not adjectives added after design; they can change structure, boundaries, runtime and interfaces.

Reasoning

Performance, availability, security, modifiability and auditability create different architectural pressures and trade-offs.

Use in practice

Express quality as a scenario or evaluable criterion, then see which architecture decisions it affects.

Concrete example

Notification outage must not prevent confirmed Reservation from being stored, but delivery must be retried and observable.

quality concern → scenario/criterion → architecture pressure → trade-off
Detailed notes

This prepares L04, where quality concerns become measurable.

SWI · L03 · Architecture 31/32

Handoff to detailed design

Architecture says where responsibility and constraints live; detailed design says how they are realized inside those boundaries.

Reasoning

The boundary is not determined by notation. A class-level decision can be architectural if it affects ownership or system guarantees; a component diagram can be merely descriptive if it carries no consequence.

Use in practice

End L03 with accepted boundaries, interfaces, ownership, runtime mapping and constraints. Continue in L05 with class design, patterns, algorithms, cohesion/coupling and refactoring.

Concrete example

Architecture: Availability owns conflict evaluation. Detailed Design: AvailabilityPolicy, interval overlap algorithm, repository query and tests.

Architecture: where + why
Detailed design: how inside
Detailed notes

This slide keeps architecture deep without swallowing the rest of the course.

SWI · L03 · Architecture 32/32

Expert architecture review loop

A strong architecture can explain the chain from system claim to implementation evidence.

Reasoning

This review loop works across web systems, enterprise systems, embedded systems, automotive, safety and security contexts. The domain changes, but the reasoning structure remains.

Use in practice

Ask the same expert questions: what claim is protected, who owns it, why this boundary, what alternative was rejected, what downside accepted, what evidence shows it still holds?

Concrete example

BR-02 → lifecycle owner → consistency boundary → mechanism chosen → state mutation rule → conformance/verification evidence.

claim → owner → boundary → alternative → downside → evidence
Detailed notes

This is the final mental model the lecture should leave behind.
