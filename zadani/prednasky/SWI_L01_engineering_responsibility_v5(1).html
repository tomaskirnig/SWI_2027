SWI · L01 · 01

Software Engineering as Engineering Responsibility

Agile delivery and AI-assisted work make engineering responsibility more visible, not less important.
Change→Decision→Implementation→Evidence→Accepted product state
Concrete example: A team adds “reservations must not overlap.” The engineering work is not finished when code compiles. It is finished only when the team knows what the rule means, where it is enforced, how it is verified, and which product state contains it.
Student notes / self-study

This lecture is not an introduction to Scrum or a list of software-process models. It starts from a practical responsibility: software changes, and someone has to keep the movement from intent to accepted product state under control. A team may be agile, plan-driven, hybrid, regulated, AI-assisted, or tool-heavy. The stable engineering question remains the same: what changed, what decision follows from it, what was implemented, what evidence supports acceptance, and what exact product state has been accepted.

Because process exists to keep change controlled, not to create paperwork.

Change request

“Confirmed reservations for the same resource must not overlap.”

Intent

What exactly counts as overlap?

State

Do draft reservations count?

Decision

Application logic, DB constraint, transaction, or both?

Evidence

What test proves enough?

Product state

Which commit/config contains it?

Student notes / self-study

A concrete change is the best starting point because it immediately shows why the course topics exist. Requirements are needed because the rule must be stated precisely. Architecture is needed because consistency must be enforced somewhere. Verification is needed because the team must know what the evidence shows. Configuration and release are needed because a team must identify exactly where the accepted change lives.

SWI · L01 · 04

From Feature Request to Engineering Chain

The visible task is small; the affected engineering chain is longer.
Stakeholder need: no double booking
Requirement: reject overlapping confirmed reservation
Driver: consistency under concurrent requests
Decision: enforcement strategy
Implementation: service + persistence + transaction
Evidence: unit + integration + selected concurrency check
Release: tagged product state + config
Student notes / self-study

This chain is not a bureaucratic template. It is a way to see whether a change is coherent. A weak team may implement a service method but never define the exact requirement. Another team may write a good requirement but never connect it to verification. Another may have tests but no release identity. The course repeatedly asks whether the chain is coherent enough for the context.

SWI · L01 · 05

A Requirement Is Not a Wish and Not a Design Decision

Requirements say what must be true; design decisions say how the system will make it true.
Weak statementWhy weakBetter direction
“Use PostgreSQL to avoid conflicts.”Solution disguised as requirement“The system shall prevent two confirmed reservations of the same resource from overlapping.”
“Reservation must be user-friendly.”Not verifiableDefine a concrete scenario or acceptance criterion
“Notify users immediately.”Hidden timing assumptionDefine what must happen if notification is delayed or fails
Student notes / self-study

This slide connects L01 to the next lecture. Many software failures start when teams confuse requirements, design choices, constraints and assumptions. PostgreSQL may be a good design choice, but it is not the requirement itself. “User-friendly” may express a real concern, but it is not usable until made concrete. “Notify immediately” may hide a dependency assumption that later breaks the system.

SWI · L01 · 06

Assumptions Are Engineering Objects

An assumption is acceptable when it is explicit; it is dangerous when it silently controls the design.

Hidden assumption

Notification service always responds quickly.

Design consequence

Reservation confirmation waits synchronously for notification.

Alternative

Reservation succeeds first; notification is retried asynchronously.

Why this matters: if notification failure should not invalidate a reservation, synchronous notification in the confirmation path may be the wrong decision.
Student notes / self-study

Assumptions are not automatically bad. Engineering always operates under incomplete knowledge. The problem is when a material assumption remains hidden. If the Notification Service is outside the reservation system, the team must decide whether notification is part of reservation success or only a side effect. This decision changes architecture, tests, error handling and release risk.

SWI · L01 · 07

Architecture Starts When a Decision Has Consequences

A diagram is useful only when it helps reason about responsibility, boundary, dependency or change.
Decision optionStrengthRisk / consequence
Check overlap only in application serviceSimple to understandMay fail under concurrency if persistence does not protect it
Use DB constraint / transactionStronger consistencyMore persistence coupling and error-handling complexity
Use reservation lock / resource aggregateExplicit domain responsibilityMore design complexity
Architecture driver: consistency of confirmed reservations when requests arrive concurrently.
Student notes / self-study

Architecture is not introduced as a set of boxes. It begins when a decision has consequences for future change, correctness, evidence or operation. The overlap rule can be enforced in different places. Each option has a trade-off. The team needs a rationale because later changes may force the decision to be revisited.

SWI · L01 · 08

Engineering Process = Controlled Movement of Change

Process is not Scrum. Process is how the team keeps engineering responsibility covered.
1Change entersissue / request / incident
2Understandintent, assumptions, impact
3Decidealternative, rationale
4Implementcode / config / data
5Verifytests / measurement / review
6Integratereviewed state
7Releaseknown version
8Learnoperation → change
Student notes / self-study

This is the central process concept for the course. The process does not have to be heavy, but the responsibilities must be covered. A small student project may use a lightweight issue, a short review, a build, one test and a small decision note. A regulated or high-consequence system needs stronger mechanisms. The underlying question is always: how do changes move through the system without losing intent, control and evidence?

SWI · L01 · 09

Agile Shortens the Loop; It Does Not Remove the Loop

Small batches and fast feedback make engineering control more frequent.

Large-batch change

Many decisions accumulate before integration and verification.

long feedback distance

Agile / small-batch change

Small change → review → verify → integrate → feedback.

short feedback distance
Reservation example: implement only “create draft reservation” first, verify persistence, then add confirmation and overlap protection as a controlled next increment.
Student notes / self-study

The lecture deliberately does not teach Scrum as the main topic. Agile is used here as a realization of fast engineering feedback. Smaller increments are useful because they reduce risk and make evidence available earlier. But small increments still need requirements, design decisions and verification. “We are agile” is not an engineering argument by itself.

SWI · L01 · 10

Framework ≠ Engineering Process

A team can run ceremonies perfectly and still have weak engineering.
A framework may help with…Engineering still has to decide…
work visibility and cadencewhat the requirement actually means
prioritization and feedback eventswhich architecture option is justified
team coordinationwhich evidence is sufficient for acceptance
continuous improvementwhich product/configuration state is releasable
Student notes / self-study

This is why the course does not become a Scrum course. Scrum may be useful, but it does not answer whether the overlap requirement is well defined, whether a database constraint is justified, whether tests cover the risk, or what exact release state is being accepted. A team can use Scrum well and engineer poorly; a team can also engineer well without using Scrum terminology.

SWI · L01 · 11

Review Is Not a Ceremony; It Is a Control Point

The value of review depends on what risk it controls.

Weak review

“Looks good.” Reviewer checks formatting and naming only.

Engineering review

Reviewer checks: intended rule, affected state, boundary behavior, tests, and release impact.

Example review question: If two confirm requests arrive concurrently, what protects the overlap rule?
Student notes / self-study

The first exercise asks teams to perform one real review cycle. The reason is not to teach Git mechanics. The reason is to make process concrete: a second person should examine something that matters. In this example, a useful review asks whether the implementation actually protects the business rule, whether tests relate to the claim, and whether assumptions are visible.

SWI · L01 · 12

Evidence Must Match the Claim

Green tests are evidence, not a magic certificate of correctness.
ClaimEvidenceWhat it does not prove
Overlap function computes correctlyunit test with selected intervalsDB behavior, concurrency, integration
Reservation is persistedrepository/integration testbusiness rule correctness
Concurrent confirms are safeselected concurrent scenarioall schedules, all production configs
Engineering habit: state not only what evidence supports, but also what it does not support.
Student notes / self-study

The course does not treat “more tests” as the goal. The goal is better reasoning between claims and evidence. A unit test may be excellent evidence for a pure overlap function and weak evidence for concurrent reservation confirmation. An integration test may prove persistence behavior and still not prove behavior under production load. Engineering maturity includes knowing the limits of your own evidence.

Configuration management appears early because it connects to almost every later topic. Students often believe that a Git commit fully identifies the product. It may not. A different database schema, feature flag, dependency version or runtime configuration can produce different behavior. Later in the course this becomes important for releases, rollback and incident analysis.

Student notes / self-study

Changeability is not an abstract quality attribute. It becomes visible when a change arrives. If adding SMS notification forces changes in five unrelated classes, the design has a different changeability profile than if it affects only an adapter behind a stable boundary. If adding WAITING_FOR_APPROVAL breaks unclear state handling, the team learns something about responsibilities and assumptions.

SWI · L01 · 15

When Failure Matters More, Rigor Must Change

The same reservation operation may need different controls in a higher-consequence context.
ContextFailure consequenceProportional rigor
Study room bookingannoyance, lost timebasic review and tests
Company vehicle bookingoperational disruption, coststronger audit trail and approval
Hazardous lab equipmentphysical harm or legal issueauthorization, stronger review, recovery and independent evidence may be justified
Student notes / self-study

This slide introduces a core engineering principle for later safety, security and assurance examples. The same technical behavior can have different consequences. A double booking of a study room is inconvenient. A double booking of hazardous equipment may create real harm. The answer is not to add maximum process everywhere. The answer is to increase rigor where the consequence and uncertainty justify it.

SWI · L01 · 16

Tailoring: What Changes Across Contexts?

Tailoring means choosing appropriate controls and evidence for the situation.
DriverLightweight internal toolHigher-consequence service
Requirement precisionsmall set of explicit rulesstronger ambiguity control and traceability
Architecture decisionsshort ADR for important choicesmore explicit alternatives and consequences
Verificationrelevant automated checkscomplementary and possibly independent evidence
Releasetag + rollback notestricter gates, config identity, recovery plan
Student notes / self-study

Tailoring is often misunderstood as reducing work. In this course it means matching engineering mechanisms to context. A student project can be lightweight because the consequence is low and learning is the goal. But it still needs a coherent chain. A higher-consequence system needs stronger evidence and control, not because a methodology says so, but because the decision risk is higher.

SWI · L01 · 17

Automation Can Produce Artifacts; It Cannot Accept Responsibility

AI may generate a consistent package that still shares one wrong assumption.
AI-generated requirement
AI-generated ADR
AI-generated code
AI-generated tests
Failure example: AI assumes notification must succeed before reservation is confirmed. Requirement, design, code and tests all agree. The package is internally consistent and still may be wrong for the business context.
Student notes / self-study

The course does not police AI use in project work. Instead, it assumes that AI may contribute to requirements, design, code, tests and documentation. The engineering problem is acceptance. A human team must still be able to ask whether the generated package implements the right intent, whether assumptions are valid, whether evidence is independent enough, and whether the release risk is acceptable.

SWI · L01 · 18

Four Failure Modes to Avoid

Poor engineering can hide behind both chaos and impressive tooling.

No process

Changes happen ad hoc; nobody reconstructs why.

Process theatre

Ceremonies exist, but do not control real decisions.

Tool theatre

Git, CI and dashboards are treated as proof of quality.

Automation theatre

Generated artifacts agree, so the team assumes they are correct.

Student notes / self-study

These failure modes are useful diagnostic categories. A team with no process loses control. A team with process theatre creates documents and events that do not affect engineering decisions. A team with tool theatre confuses pipelines with quality. A team with automation theatre trusts generated consistency too much. The course repeatedly asks students to connect mechanisms to real engineering control.

One small reservation system becomes richer through repeated engineering questions.

Why one system? Students see consequences of earlier choices instead of producing disconnected weekly documents.

The course uses the same system so that decisions have consequences. Requirements written in week 2 affect architecture in week 3. Architecture affects changeability in week 5. Tests and measurements become evidence in week 6. Release identity matters in week 8. This is closer to real engineering than isolated weekly artefacts.

SWI · L01 · 20

C01: Start the Engineering Project

The first exercise defines the system and proves one small technical thing.

Define

Reservation domain, Resource, Reservation, User, states, rules, boundary, assumption, unknown.

Execute

One real engineering spike: persistence, boundary failure, or reproducible build/config.

C01 is not: a complete implementation of the reservation system. The walking skeleton is defined now and must become runnable after C03 / before C04.
Student notes / self-study

This clarifies the first exercise. Students define the intended reservation system, but they do not implement all operations in C01. They must execute one engineering spike to reduce one uncertainty or prove one technical assumption. This establishes the habit Question → Probe → Evidence → Decision. The first meaningful end-to-end product slice is required later, after requirements and architecture work.

SWI · L01 · 21

CP1 Checks the First Engineering Chain

After C03, CP1 asks whether intent, requirements, architecture, running software and evidence are connected.
Project Frame
5–8 core requirements
Architecture drivers + alternatives + ADR
Runnable walking skeleton
Verification evidence
Exact checkpoint state
Operational rhythm: teams freeze CP1 before C04; instructors review CP1 during C04 while teams start C04 work.
Student notes / self-study

The checkpoint is not a presentation competition. It checks the coherence of the first engineering chain. The exact reviewed state must be identifiable by tag or commit. Reviews happen in the next exercise because an instructor may need to inspect several teams. This avoids judging teams by how quickly they finish within one 90-minute slot.

SWI · L01 · 22

What to Keep From L01

The rest of the course repeatedly applies these ideas in more concrete forms.
1Software Engineering is controlled change, not only implementation.
2Process controls intent, decisions, evidence and product state.
3Agile shortens feedback loops; it does not remove engineering responsibility.
4Evidence must match the claim and state its limitations.
5Automation can produce artifacts; engineers still accept or reject the result.
Student notes / self-study

If the details are forgotten, these five ideas should remain. They explain why the next lectures exist. Requirements make intent precise. Architecture structures decisions. Quality and verification create evidence. Risk changes rigor. Configuration and release identify product state. Operation creates new evidence. Automation requires qualified ownership rather than blind trust.
