From Requirements to an Engineering Specification

A good specification is not a pile of “shall” sentences. It is an accepted model of what must be true.

  • Semantics · boundaries · attributes · scenarios · quality · evidence · change
  • Running case: a reservation system with Create, Availability, Confirm, Cancel
  • Engineering outcome: know what you accept before AI generates tests or code

Running example

  • Resource: laboratory equipment
  • Rule: confirmed exclusive reservations must not overlap
  • Baseline states: DRAFT → CONFIRMED → CANCELLED
  • Change later: selected resources require approval
Student notes. This lecture is broader than the exercise. The exercise applies the ideas, but the lecture should teach the engineering concepts. The core idea is ownership: students may use AI to create requirements, diagrams, tests and code, but they must be able to explain the accepted meaning, boundary, verification and change impact of each important claim.

Learning contract

The target: accept the meaning, not the text

After L02, “AI wrote it” is not an explanation.

  • Read generated requirements and detect hidden ambiguity
  • Distinguish need, requirement, business rule, constraint, assumption and design decision
  • Connect text to scenarios, state models, boundaries, verification and running behavior
  • Reason about change before rewriting everything

Expected explanation

  • Weak: “AI generated a requirements list.”
  • Strong: “We accept REQ-03 because it defines when a DRAFT reservation may become CONFIRMED, and these three examples verify it.”
Student notes. The lecture is successful if students stop treating requirements as a document-production task. They should see specification as an engineering model that can be challenged, tested, changed and used to guide architecture.

02
Engineering loop

Why L02 comes after L01

Before you implement, verify or release, you need to know which claim is being judged.

  • L01: change must be controlled by engineering responsibility
  • L02: the team makes the accepted claims explicit
  • C02: the team turns those claims into a running baseline
  • C03: architecture decides how the baseline should be structured

Example chain

  • Change: “Some equipment needs supervisor approval.”
  • Claim: reservation must not reach CONFIRMED without approval
  • Evidence: delayed, rejected and expired approval cases are verified
  • Architecture driver: persisted workflow / asynchronous state handling
Student notes. This slide connects the course. Requirements are not a phase before engineering; they are part of the decision loop. Without an explicit claim, a team cannot judge whether a generated implementation is correct, incomplete or simply based on a different interpretation.

03
Running case

The apparently clear rule

“Confirmed reservations for the same resource must not overlap.”

  • This sounds clear enough to implement
  • It is not clear enough to engineer safely
  • Examples reveal hidden semantics

Attack the sentence

  • [10:00,11:00] and [11:00,12:00] — overlap or not?
  • Does PENDING_APPROVAL block the resource?
  • Is the resource exclusive or capacity-based?
  • What if two confirmations happen concurrently?
  • Which clock defines the interval?
Student notes. The rule is intentionally simple. Its purpose is to show that ambiguity often hides inside ordinary business language. More text does not automatically solve the problem; the specification needs precise semantics and evidence.

04
Core model

Specification = accepted claims + supporting views

No single artifact is the specification. The specification is the coherent set of accepted engineering claims.

  • Textual requirements state what must hold
  • Business rules and invariants state what must never be violated
  • Scenarios explain behavior under conditions
  • State models define legal transitions
  • Boundaries define responsibility and failure meaning
  • Verification examples show how claims are judged

One behavior, several views

  • Text: DRAFT can become CONFIRMED only if no conflict exists
  • Invariant: no two CONFIRMED reservations overlap
  • Scenario: user requests confirmation and conflict check rejects overlap
  • Statechart: DRAFT → CONFIRMED only under guard
  • Test: concurrent conflict → at most one confirmed
Student notes. This is the main conceptual frame. Students should stop asking “Which document is the SRS?” and start asking “Do these claims and views agree, and can another engineer use them to design, implement and verify the system?”

05
Boundary

System boundary: where responsibility starts and stops

A requirement without a boundary often assigns responsibility to the wrong system.

  • Inside boundary: reservation lifecycle, rules, state changes, conflict decisions
  • Outside boundary: identity provider, notification delivery, payment, maintenance planning
  • At boundary: interface contract and failure semantics must be explicit

Reservation boundary

  • Reservation Service confirms or rejects reservations
  • Identity Provider authenticates users; reservation system consumes identity claims
  • Notification Service sends messages; reservation system decides what happens if notification fails
  • Equipment maintenance system may mark Resource inactive; reservation system reacts to that state
Student notes. Boundary is not only a box in a diagram. It is an ownership decision. If Notification Service is unavailable, does reservation confirmation fail, succeed with retry, or succeed with a warning? That is a specification decision at the boundary.

06
Requirement attributes

Complete requirement record: the minimum anatomy

A useful requirement is more than the sentence after “shall”.

  • Identity: ID, name, type, status, version, owner/source
  • Meaning: terms, data, state, boundary, assumptions
  • Condition: trigger, preconditions, postconditions, failure outcomes
  • Evidence: verification method, examples, acceptance criteria
  • Links: rationale, business rule, scenario, state view, tests, architecture drivers

REQ-03 record skeleton

  • ID: REQ-03 Confirm Reservation
  • Source: double-booking prevention rule
  • Precondition: Reservation.state = DRAFT
  • Postcondition: state = CONFIRMED and invariant still holds
  • Verification: no conflict, overlap, boundary, concurrent conflict
Student notes. This is the slide that should prevent shallow requirements. The statement itself is just one field. Missing preconditions, postconditions, failure outcomes or verification examples usually means that the team has not really accepted the requirement yet.

07
Classification

Need, requirement, rule, constraint, assumption, decision

Different statements require different treatment. Do not call everything a requirement.

  • Need: why the system exists
  • Requirement: observable behavior or property that must hold
  • Business rule: domain rule, often cross-cutting
  • Constraint: externally imposed limit on solutions
  • Assumption: treated as true but not guaranteed
  • Design decision: chosen way to satisfy claims

Same domain, different meanings

  • Need: users need to reserve equipment
  • Requirement: system rejects overlapping confirmation
  • Rule: no two confirmed reservations overlap
  • Constraint: university identity provider must be used
  • Assumption: notifications are not atomic with confirmation
  • Decision: use PostgreSQL with optimistic locking
Student notes. This distinction matters in review and change. A constraint may not be negotiable. A design decision can be changed. An assumption must be validated or protected against. A business rule may affect several operations, not just one use case.

08
Shall-style requirements

“Shall” gives grammar, not semantics

A grammatically correct requirement can still be underspecified.

  • Bad but common: “The system shall prevent overlapping reservations.”
  • Better: name the state, resource type, interval semantics and observable result
  • Shall is useful for obligation, but it does not define the missing meaning

Upgrade the sentence

  • Vague: system shall prevent overlaps
  • Precise: when confirming a DRAFT reservation for an exclusive Resource, the system shall reject confirmation if its [start,end) interval overlaps an existing CONFIRMED reservation of that Resource
  • Still missing? concurrency, override, capacity-based resources
Student notes. Automotive-style “shall” wording is useful, especially in high-rigor contexts. But students must learn that syntax does not replace semantics. A requirement that sounds formal can still let implementers invent the real behavior.

09
Functional behavior

Functional requirement = observable contract

The requirement should say what the system must make true, not how the team currently plans to code it.

  • Observable means visible through the system boundary or persistent state
  • It should not prescribe a mechanism unless the mechanism is externally required
  • Architecture later chooses transactions, locks, constraints, queues or services

Confirm reservation contract

  • Observable: at most one conflicting reservation becomes CONFIRMED
  • Not required here: use SERIALIZABLE isolation
  • Not required here: lock table RESERVATION
  • Possible later design: DB constraint, optimistic lock, transactional service, command queue
Student notes. This is the bridge to C03. Requirements constrain the solution space; architecture chooses within that space. If the requirement prescribes a mechanism too early, students may hide design decisions inside specification.

10
Rules that cut across operations

Business rules and invariants

Some truths must hold globally, not just during one scenario.

  • Business rule: domain rule the system must respect
  • Invariant: a rule that must remain true in every committed state
  • Invariants often expose concurrency and architecture needs

Exclusive resource invariant

  • BR-02: At no committed system state may two CONFIRMED reservations overlap for the same exclusive Resource
  • Create may create DRAFT without blocking
  • Confirm must preserve BR-02
  • Cancel must release availability if it changes CONFIRMED to CANCELLED
  • Availability must compute results using the same blocking semantics
Student notes. A common mistake is to bury a global rule inside one use case extension. If no-overlap is an invariant, every operation that can change or query reservation state must be consistent with it.

11
Quality attributes

Quality requirement: condition + measure + target

“Fast”, “reliable” and “usable” are not quality requirements until they are measurable under defined conditions.

  • Condition: under what load, data size, environment or failure mode?
  • Measure: latency, throughput, availability, recovery time, error rate, coverage, etc.
  • Target: explicit value with rationale or marked TBD if unknown
  • Verification: load test, monitoring, fault injection, review, analysis

Availability query quality

  • Weak: availability search shall be fast
  • Better: under 50 concurrent users and 10,000 future reservations, 95% of availability checks complete within 500 ms
  • If 500 ms has no source: mark target TBD rather than invent precision
Student notes. This slide keeps quality in L02 without turning it into a full quality lecture. The important message is that quality requirements shape architecture and tests. Fabricated numbers from AI are dangerous because they look precise but have no authority.

12
Solution space

Constraint vs design decision

The same sentence can be a requirement or a design decision depending on its source.

  • Constraint: imposed by customer, regulation, platform, environment, contract
  • Design decision: selected by the team as a means to satisfy claims
  • Hidden design decisions inside requirements reduce future changeability

PostgreSQL example

  • Constraint: “The university platform mandates PostgreSQL.”
  • Decision: “We choose PostgreSQL because it supports transactions and is available in our stack.”
  • Bad requirement: “The system shall use PostgreSQL” without source or rationale
Student notes. Students often write technology choices as requirements. The review question is simple: must this be true from outside the team, or did we decide to make it true this way?

13
External boundaries

Interfaces and boundary failure semantics

A boundary is incomplete until failure meaning is defined.

  • Interface purpose: why the dependency exists
  • Inputs/outputs that matter to the requirement
  • Failure modes: timeout, unavailable, invalid response, duplicate response
  • Policy: does operation fail, succeed with retry, degrade, compensate or queue?

Notification Service

  • Claim: confirmed reservation should notify the user
  • Question: if Notification Service times out, is reservation confirmation rolled back?
  • Option A: confirmation fails if notification fails
  • Option B: confirmation succeeds; notification is retried asynchronously
  • Option C: confirmation succeeds but user sees degraded notification state
Student notes. This is where boundaries become concrete. “There is a Notification Service” is not enough. The system must define whether notification is part of the transaction or a separate obligation. That decision affects requirements, tests and architecture.

14
State model

State semantics: behavior lives in transitions

Many requirements only become clear when legal states and transitions are explicit.

  • Each state has meaning: DRAFT, CONFIRMED, CANCELLED
  • Each transition has trigger, guard and postcondition
  • Operations must agree with the state model
  • Change may introduce new states such as PENDING_APPROVAL

Baseline lifecycle

  • [initial] → DRAFT by Create Reservation
  • DRAFT → CONFIRMED by Confirm Reservation if conditions hold
  • DRAFT → CANCELLED by Cancel if policy allows
  • CONFIRMED → CANCELLED by Cancel if policy allows
  • No transition from CANCELLED back to CONFIRMED unless explicitly specified
Student notes. The state model should not be decoration. It is a precise view of semantics. If the textual requirement says CONFIRMED can be cancelled but the state model omits the transition, the specification is inconsistent.

15
Operation contract

Preconditions, postconditions and failure outcomes

A scenario describes flow; pre/postconditions define what must already hold and what the operation guarantees.

  • Precondition: what must be true before the operation is valid
  • Success postcondition: what becomes true after success
  • Failure outcome: what remains unchanged or what error is visible
  • Invariant: what must remain true in every committed state

Confirm contract

  • Pre: Reservation exists; state = DRAFT; Resource active
  • Success: state = CONFIRMED; Resource blocked for interval; no-overlap invariant still true
  • Failure: conflict → state remains DRAFT; reason returned
  • Invariant: no double booking of exclusive Resource
Student notes. This slide gives students the vocabulary for operation slices. It also catches circular definitions: “confirm if all conditions are met” is weak until the conditions and the resulting state are explicit.

16
Scenario view

Scenario: behavior under concrete conditions

A scenario forces a requirement into a sequence of events and exposes missing alternatives.

  • Scenario is useful for one goal and one path through behavior
  • It must include preconditions, trigger, main success steps and meaningful alternatives
  • It is not the complete specification by itself

Confirm Reservation scenario

  • Pre: Reservation is DRAFT; Resource is active
  • 1. User requests confirmation
  • 2. System checks source state
  • 3. System evaluates conflicts
  • 4. If no conflict, system changes state to CONFIRMED
  • 3a. Conflict exists → reject, state remains DRAFT
  • 2a. Invalid state → reject, state unchanged
Student notes. The scenario should not be a UI-click script. It describes system behavior and decision points. Extensions are not decoration; they reveal failures, missing rules and verification cases.

17
Actor-goal view

Use-case view: actors and goals, not internals

Use-case visualization answers who wants which system goal. It does not replace requirements, rules or states.

  • Use it for system boundary, actors and goals
  • Do not put database tables, classes or internal services into the use-case view
  • Use include/extend only when it clarifies real goal structure

Reservation system goals

  • User → Create Reservation
  • User → Check Availability
  • User → Confirm Reservation
  • User → Cancel Reservation
  • Approver appears only after approval workflow is introduced
  • Notification Service is not a primary actor unless it has an external goal against this system
Student notes. Students know use cases, so this slide should not reteach UML notation. The advanced point is consistency: every goal in the use-case view should have specified behavior, and every core operation should be visible as a system goal when appropriate.

18
Examples as evidence

Acceptance examples: requirements become executable thinking

Examples reveal boundary choices faster than abstract wording.

  • Use examples for success, failure, boundary and concurrency cases
  • Examples must reflect the accepted semantics
  • If examples contradict the text, the specification is not coherent

Availability examples

  • Existing CONFIRMED reservation: [10:00,11:00)
  • Query [09:00,10:00) → AVAILABLE
  • Query [10:30,11:30) → UNAVAILABLE
  • Query [11:00,12:00) → AVAILABLE
  • This encodes [start,end) interval semantics
Student notes. Acceptance examples are not just tests at the end. They are a way to discover whether the text has enough meaning. If the example at 11:00 is not agreed, implementation will invent the boundary rule.

19
Time is not prose

Temporal semantics: before, after, until, within

Time words carry technical meaning. Specify the clock and the boundary.

  • “Before start time” — strictly before or before-or-at?
  • Which clock: server, user locale, Resource location, external provider?
  • Which instant: request received, validation completed, transaction committed?
  • What happens when operations race?

Cancel policy

  • REQ: a CONFIRMED reservation may be cancelled before start time
  • Precise: request must be received before Reservation.start according to server UTC clock
  • Alternative: cancellation is valid if transaction commits before start
  • Different choice → different tests and architecture
Student notes. Temporal semantics often look like small details, but they determine observable behavior. If AI fills in a clock or boundary without justification, the team must either accept it explicitly or mark it unresolved.

20
Parallel behavior

Concurrency is sometimes a requirement problem

If concurrency changes business correctness, the observable result belongs in the specification.

  • Sequential scenario: check availability → confirm
  • Concurrent reality: two users can confirm conflicting reservations at once
  • The requirement should state the observable outcome
  • Architecture later decides how to enforce it

Double-booking race

  • A checks interval → free
  • B checks same interval → free
  • A confirms
  • B confirms
  • Accepted claim: for conflicting confirmations, at most one reaches CONFIRMED
Student notes. This is one of the most important graduate-level points. A scenario can be correct sequentially while the system still violates the invariant under concurrency. That is not merely a coding problem; it is an incomplete specification.

Consistency

Cross-view consistency: the specification must agree with itself

A correct sentence can still be wrong inside an inconsistent model.

  • Textual requirement
  • Scenario
  • Statechart
  • Use-case view
  • Acceptance examples
  • Running application

Inconsistency example

  • Text: CONFIRMED can be cancelled before start
  • Statechart: CONFIRMED has no transition to CANCELLED
  • Example: cancellation after start is accepted
  • Application: deleting row removes audit history
  • Result: the team has not accepted one coherent semantics
Student notes. This slide should connect lecture to exercise. Students must not produce independent artifacts that all look polished. They must reconcile them. Cross-view disagreement is a defect in the specification, not a harmless difference in notation.

Evidence

Verification idea: the first quality filter

A requirement is not ready until the team can say how it would be judged.

  • Verification idea is not always a full test case yet
  • It names the observation or analysis that would demonstrate satisfaction
  • It often reveals missing state, boundary, time or concurrency semantics

Verification for Confirm

  • No overlap → confirmation succeeds
  • Overlap → confirmation rejected
  • Boundary-touching intervals → result follows [start,end)
  • Two concurrent conflicting confirmations → at most one CONFIRMED
  • Inactive Resource → rejected, state unchanged
Student notes. This is not testing lecture yet. It is specification discipline. When students cannot propose a verification idea, the requirement is probably too vague, too broad or too solution-oriented.

Traceability

Traceability is a dependency graph for change

Traceability is not a bureaucratic matrix. It is how we navigate impact and evidence.

  • Backward: why does this claim exist?
  • Forward: what depends on this claim?
  • Change impact: what becomes questionable when the claim changes?
  • Evidence: which test, analysis or review supports it?

Minimum useful chain

  • Goal: avoid double booking
  • → BR-02 exclusive Resource invariant
  • → REQ-03 Confirm Reservation
  • → Scenario extension: conflict exists
  • → Verification: overlap and concurrent conflict examples
  • → Architecture driver: atomic conflict resolution
Student notes. Students do not need a giant traceability matrix in C02. They need enough links to reason about change. In high-rigor environments the same idea becomes stricter, more complete and more controlled.

Versioned specification

Baseline: accepted now, not true forever

A baseline makes change visible. It does not freeze learning.

  • Baseline v0.1: accepted current behavior
  • Change card: approval may be delayed, rejected or expire
  • Impact analysis: identify affected and unaffected claims
  • Baseline v0.2: updated accepted behavior
  • Implementation must be checked against the accepted baseline

Baseline change

  • v0.1: DRAFT → CONFIRMED under conflict rules
  • Change: some resources require approval
  • v0.2: DRAFT → PENDING_APPROVAL → CONFIRMED / REJECTED / EXPIRED
  • Unaffected: Create may still create only DRAFT
Student notes. This slide should prevent students from rewriting everything after change. Good impact analysis distinguishes what actually changed from what remains valid.

Change reasoning

Change impact: approval workflow

Do not rewrite the whole specification. First ask what the change invalidates.

  • New actor? Approver
  • New operation? Approve Reservation
  • New state? PENDING_APPROVAL, REJECTED, EXPIRED
  • Changed availability semantics? Pending blocks or not?
  • Changed cancellation semantics? Can pending be cancelled?
  • New verification examples and architecture drivers

Impact map

  • Create: may remain unchanged — still creates DRAFT
  • Confirm: may become request-for-confirmation or transition to pending
  • Availability: must decide whether pending blocks capacity
  • Cancel: must decide pending cancellation
  • Architecture: persisted workflow, expiry timer, notification boundary
Student notes. This is the heart of change engineering. The correct answer is not “edit all requirements”. The correct answer is to identify the claims and views whose meaning changed, and to justify why others still hold.

Requirements ↔ architecture

Architecture feedback creates derived requirements

Requirements do not only flow into architecture. Architecture can reveal new requirements.

  • Stakeholder claim may be simple
  • Architecture decision exposes obligations
  • Derived requirements make those obligations explicit
  • The specification and architecture co-evolve

Notification unavailable

  • Claim: reservation confirmation should not fail only because notification is unavailable
  • Architecture choice: asynchronous notification delivery
  • Derived requirements: store pending notification, retry policy, duplicate handling, permanent failure visibility
  • C03 then decides components and responsibilities
Student notes. This connects L02 to L03. The first architecture decision may reveal requirements that were not visible at stakeholder level. In automotive/high-assurance this relationship must be controlled and traceable.

Rigor is contextual

Agile and high-rigor practice use the same questions

Lightweight does not mean implicit. High rigor does not mean document theatre.

  • Normal product: enough explicit semantics to build, test and change safely
  • Automotive/high-assurance: stronger attributes, traceability, feasibility analysis, evidence and change control
  • Same core questions; different justified rigor

Same question, different rigor

  • Business reservation app: rule + statechart + acceptance examples + code evidence may be enough
  • Automotive-like high consequence: source, attributes, bidirectional traceability, feasibility, operating environment impact, verification criterion and controlled baseline
  • Both must know what is accepted and how it is verified
Student notes. This slide should avoid the false opposition “agile versus standards”. Agile still needs explicit accepted behavior; high-rigor domains need stronger evidence because the consequence of being wrong is higher.

Qualified ownership

AI-native requirement work: what is still human-owned?

AI can draft. The team accepts, rejects or corrects.

  • AI may generate requirements, scenarios, diagrams, tests and code
  • The team owns accepted meaning, rationale, consistency and evidence
  • Generated precision without source is suspect
  • Generated code must be checked against accepted specification

Four ownership checks

  • Can we explain REQ-03 without reading the generated text?
  • Can we show one example that falsifies it?
  • Does the app behavior match it?
  • What changed when approval was introduced?
Student notes. This slide directly addresses the course reality. The question is not “Did students use AI?” but “Can they take qualified ownership of the result?”

Detailed example

Full operation slice: Create Reservation

A slice is one operation specified as a compact, testable contract.

  • Goal: record user intent without allocating the Resource
  • Trigger: authorized user requests Resource + interval
  • Preconditions: user authorized, Resource exists, start < end
  • Postcondition: one DRAFT reservation exists; no allocation committed
  • Failures: unauthorized, unknown Resource, invalid interval
  • Verification: valid create; start == end rejected; unknown Resource rejected

Important semantic decision

  • Create does not check overlap in this policy because DRAFT does not block Resource
  • If your domain wants Create to hold capacity, the requirement, state model, availability and tests must all change
Student notes. This slide aligns exactly with C02 but teaches the principle: every operation should expose what it does and what it deliberately does not do. The “does not allocate Resource” part is a meaningful specification decision.

Detailed example

Full operation slice: Confirm Reservation

Confirm is the point where the reservation becomes an accepted allocation.

  • Goal: turn a valid DRAFT into CONFIRMED allocation
  • Preconditions: reservation exists; state = DRAFT; Resource active
  • Success: state = CONFIRMED; Resource blocked; invariant preserved
  • Failures: inactive Resource, overlap, invalid source state
  • Concurrency: conflicting confirmations → at most one CONFIRMED

Better than circular wording

  • Weak: confirm if all conditions are satisfied
  • Concrete: confirm only if Resource is active and interval does not conflict with existing CONFIRMED reservation
  • Observable result: rejected conflicts remain DRAFT
Student notes. This is the corrected example. It avoids circular definitions and names the conditions. It also shows why concurrency belongs to specification when it affects double booking.

Detailed example

Full operation slice: Cancel Reservation

Cancel must define domain-visible outcome, not database deletion.

  • Goal: withdraw an eligible reservation
  • Policy example: DRAFT or CONFIRMED may be cancelled before start time
  • Success: state = CANCELLED; it no longer blocks availability
  • Failures: already cancelled, after start, invalid state
  • Time semantics: clock and boundary must be explicit

Decision points

  • Repeated Cancel: idempotent success or explicit rejection?
  • At start time: allowed or rejected?
  • Cancel racing with Confirm: which observable outcome is accepted?
  • Audit: cancelled reservation may remain stored even if no longer active
Student notes. This slide is important because students often treat Cancel as Delete. Domain semantics should be independent from storage mechanics.

Exercise handoff

What C02 will practice

C02 applies the lecture to the team’s reservation system.

  • Create four complete operation slices
  • Define shared rules and invariant once
  • Create use-case / actor-goal view and lifecycle statechart
  • Generate a running app from accepted baseline
  • Execute verification examples
  • Apply approval change and update affected parts only
  • Carry architecture drivers into C03

Expected final state

  • Accepted Baseline v0.2
  • Running AI-generated application
  • Evidence: examples executed and mismatches resolved
  • Architecture driver: e.g. persisted approval workflow or atomic conflict resolution
Student notes. This is not a substitute for the exercise instructions. It explains why the exercise is designed as it is. Students should understand that the running app is intentionally allowed to have poor architecture; C03 will deal with structure.

Summary

Final takeaway

A specification is the team’s accepted explanation of what must be true.

  • Not only a list of requirements
  • Not only a use-case diagram
  • Not only a generated document
  • Not only tests
  • Not only running code
  • It is the coherent model that connects all of them

Ownership sentence

  • “We accept these claims, know their meaning, can show evidence, and understand what changes when the context changes.”
Student notes. End with the ownership message. This is the link from specification to architecture, quality and later release/operation.
